## 1. Two premises were resolved before any code was written

The order was halted twice on entry and both were answered by Michael.

**Day boundary — option A.** Report **UTC** quanta to the Chief. Leave
`spend_today_usd` and the `$100` cap on **Asia/Jerusalem**, untouched. Add a
distinct UTC-scoped status field and bind the agreement test to *that* field.
Both fields name their window, because the Chief's card and this app's own
screen legitimately differ for three hours a day. Mirrors the Email
Followupper, whose `health.budget` carries both windows for the same reason.

Why this needed asking: the order required (a) reporting per UTC day, (b) the
status figure and the quanta agreeing on a day boundary, and (d) no change to
the `$100` cap — while (c) the status figure sat on the Jerusalem boundary and
the cap was enforced off that same sum. The order treated the status figure's
boundary as a free variable; it was welded to the cap that was out of scope.

**`initiated_by` — omitted entirely.** The Chief treats an absent value as
legacy-unattributed: counted for truth, never braking. No attribution invented,
no column added, no job identity threaded. Per-row attribution gets its own
order.

Why this needed asking: the order allowed for "honest partial attribution", but
the true answer was starker — **not one spend row is attributable**.
`llm_spend` has no `job_id`, no `user_id` and no owner; the three call sites tag
a pipeline *stage* (`classifier`, `hq-resolver`, `web-resolver`); no job
identity reaches them (`classify(landingUrl, adText)`, `resolveHq(page)`,
`resolveWebDestination(args)`), and there is no `AsyncLocalStorage` to recover
it from. With a closed set of `{chief, human}` there was no legal value to send.

## 2. Scope item 3, answered: the 2026-08-11 reading was legitimate

The Chief's card showed `spend_today_usd` at `$7.6492` all evening on
2026-08-11 and `$0.0000` at 21:00 UTC. **Both readings were correct. Nothing
was fixed, because nothing was broken.**

- **Read from the durable ledger, not an in-process accumulator.**
  `routes-chief.ts:90` → `chief.ts:871` →
  `SELECT COALESCE(SUM(usd),0) FROM llm_spend WHERE spend_day = ?`. That is the
  PostgreSQL table L-3.4g moved this app onto; a restart does not reset it.
  `chief.ts` deliberately avoids `llmBudget.spentTodayUsd()`, which swallows a
  failed read and returns 0 — right for a budget gate that must fail open,
  wrong for a status figure that must 503 rather than fabricate a zero.
- **The day boundary is Asia/Jerusalem**, and the same sum enforces the cap.
- **21:00 UTC is Jerusalem midnight.** Verified by execution rather than
  arithmetic: `jerusalemDay()` returns `2026-08-11` at `20:59:59Z` and
  `2026-08-12` at `21:00:00Z` (IDT = UTC+3 in August). The reset landed on the
  boundary to the second.

## 3. As built

| | |
|---|---|
| **Figure reported** | This app's own `llm_spend` ledger — the same rows the `$100` cap is enforced against. Summed as a RANGE over `llm_spend.ts` (absolute epoch-ms), never re-derived from anywhere else. |
| **Vendor** | `anthropic`, one today. Per-vendor by construction: a second paid vendor is another cursor row and another quantum stream, no mechanism change. |
| **Day boundary** | **UTC**, per the Chief's fleet contract. `utcDay()` / `utcDayBounds()` are the only definition, pinned as exact inverses by a unit invariant and a smoke assertion. |
| **Quanta** | `$0.50`. One HTTP request per quantum, numbered `q1..qn` within a vendor-day. The sub-quantum remainder is never rounded — it stays visible as lag. |
| **Idempotency** | `external_id = leadfinder:<vendor>:<utc-day>:q<n>`. A retry, a timeout or a crash re-sends the identical id. |
| **Attribution** | **`initiated_by` omitted entirely.** Not guessed, not defaulted. |
| **Transport** | `POST <CHIEF_URL>/api/ingest/spend`, `Authorization: Bearer <CHIEF_INGEST_TOKEN>`, `content-type: application/json`. Body is exactly five fields: `app`, `vendor`, `day`, `amount_usd`, `external_id`. |
| **Retries** | 5xx, **429** and transport errors: up to 4 attempts, 500ms linear backoff, same `external_id`. Every other 4xx: never retried, reporter latches off with one loud line. |
| **Cursor** | `chief_spend_cursor(utc_day, vendor, reported_quanta, updated_at)`, advanced only after a 2xx, monotonic via `GREATEST`. |
| **Cadence** | One sweep at boot, then every 5 minutes. 7-day lookback; a day that falls off the back still owing quanta is named out loud with its dollar shortfall. |
| **Dormancy** | Unset `CHIEF_URL` or `CHIEF_INGEST_TOKEN` ⇒ dormant, one loud warning per boot, no crash, no request. |

### Why both a cursor and an idempotent id

The cursor stops the reporter re-sending *everything* after a restart. The
deterministic `external_id` stops the one quantum that was in flight — accepted
by the Chief but not yet written to the cursor — from counting twice. Neither
is sufficient alone; both are cheap.

### What `/api/chief/status` now serves

The four fields before it are unchanged. `spend_today_usd` is untouched.

```
spend_today_usd         2.37     ← Asia/Jerusalem day; the figure the $100 cap uses
spend_today_window      "Asia/Jerusalem"
spend_today_utc_usd     2.37     ← UTC day; the scope and boundary the Chief is sent
spend_today_utc_window  "UTC"
spend_reported_quanta   4        ← $2.00 acknowledged
spend_unreported_usd    0.37     ← the cursor's lag, so a silent reporter is visible
spend_reporter          "active" ← dormant | active | latched
```

The agreement test binds to the UTC field, not to `spend_today_usd`:
`spend_today_utc_usd == spend_reported_quanta × 0.50 + spend_unreported_usd` —
asserted in the unit suite, over real HTTP in both modes, and against the quanta
the fake Chief actually received.

### What the Chief's card will show

The sum of this app's whole `$0.50` quanta for the UTC day, with no
`initiated_by`, i.e. entirely legacy-unattributed. It will trail this app's own
ledger by up to `$0.49` (the open quantum) plus whatever is in flight between
ticks. It will **not** equal `spend_today_usd` for three hours a day — from
21:00 UTC when the Jerusalem day rolls, until 00:00 UTC when the UTC day does.
That gap is the design, not a fault, and both windows are named in the response.

## 4. Amendment: 429 retries instead of latching

Built first to the order's literal rule — every 4xx latches — which meant one
rate-limit reply could silence spend reporting until the next boot. That was
flagged in the report rather than quietly deviated from, and the decision came
back to move it.

429 now takes the retry branch: same bounded backoff as a 5xx, same
`external_id`, never latches. Every other 4xx stays fatal.

The distinction is stated in the code, not implied: other 4xx codes are verdicts
on the request itself — wrong credential, unknown field, rejected id — and
repeating one loops on something that cannot succeed. A 429 says *later*, not
*wrong*; the request is well-formed and only the timing is at fault. Latching on
it would reopen the exact blind spot O-25 exists to close, for a request that was
never faulty. The Chief's ingest does not rate-limit today; it may later, and
this app will not need a code change on that day.

## 5. Two defects found on the way, both fixed here

### 5.1 A boot-blocking migration landmine

`applyMigrations()` refused **any** pending migration whenever the baseline
tables were present, offering `LEADFINDER_DB_ADOPT=1` as the way out. Correct
for the case it was written for — a schema created by something other than this
migrator, with no migration state — but the condition it actually tested was
`pending.length > 0 && baseline tables exist`, which every future migration
satisfies.

Migration `002` is the first migration after the baseline, so L-3.5a is the
first order to trip it. Left alone:

1. Production (which has `001` recorded and all nineteen tables) would have
   **refused to boot**.
2. An operator following the error's own instruction would have set
   `LEADFINDER_DB_ADOPT=1`, recording `002` as applied **without creating
   `chief_spend_cursor`** — after which no later boot would ever create it and
   the reporter would fail against a missing table forever.

Fixed by gating the adopt path on `applied.size === 0`. Adopt exists for a
database this migrator has never recorded anything in; once it owns the schema,
later migrations run. Proved in the smoke: `002` applies cleanly to a database
that already has `001`, and the adopt path still refuses an unrecorded schema
and still records-without-running under `LEADFINDER_DB_ADOPT=1`.

### 5.2 A warning that would have cried wolf every five minutes

The out-of-window notice first fired on the mere existence of ledger rows older
than the sweep window — true of every app more than a week old, so it would have
warned on every sweep forever. Narrowed to the case worth hearing: an old day
that is *still unsettled*, named with its dollar shortfall.

## 6. Mutation proofs

Each applied, observed to bite, and reverted.

| Mutation | What bit |
|---|---|
| Cursor write removed | `B: after a real restart the same days send nothing` — **35 quanta re-sent** |
| 4xx made retryable | 8 unit assertions, plus smoke `D` and `E` — the 4xx was attempted 4 times and never latched |
| UTC day shifted 3h in one place | 2 unit assertions immediately; **the smoke did not bite at first** |

The third result was the useful one. The boundary is expressed by two functions
facing opposite ways — `utcDay()` labels an instant, `utcDayBounds()` gives a
label's range — and every assertion happened to exercise only one of them, so a
three-hour shift in one slipped through. Each function looked correct in
isolation while disagreeing with the other; a reporter that enumerated days with
one and summed them with the other would drop or double-count whole hours of
spend.

Fixed by pinning the property that actually matters: **the day an instant is
labelled with must be the day whose bounds contain it** — asserted over ten
instants in the unit suite and over the real fixture rows in the smoke. The
mutation then bit in both.

### Expect this and do not report it as a bug

Between 21:00 and 24:00 UTC the Chief's card and Leadfinder's own screen show
different spend figures. Leadfinder's budget day resets at Jerusalem midnight;
the Chief counts UTC days. Both are correct and each names its window.

### Migration plan

One new migration, `002 chief spend reporting cursor`. Creates
`chief_spend_cursor` and one index, `idx_llm_spend_ts`. **Additive only** — no
table altered, nothing dropped.

### Before every publish that ships a migration

```
node scripts/align-dev-db.mjs            # dry run — shows what is pending
node scripts/align-dev-db.mjs --apply    # apply it
```

Then publish. This makes the publish-time schema diff empty. Skipping it is what
produced the incident in §9.1. Already done for this order.

### Never do this

**Never approve a generated `DROP`.** See §9.1 — the first publish attempt after
this order offered to drop the spend cursor, and approving it would have broken
reporting permanently. The rule is standing, and
`assertNoDestructiveMigrations()` enforces it for migrations this repo ships.

If a boot ever fails with an error suggesting `LEADFINDER_DB_ADOPT=1`, **do not
set it.** Post-L-3.5a that can only mean the migration state has gone missing,
and adopting would record `002` without creating its table — silently breaking
spend reporting in a way that never self-heals. Investigate instead.

## 9.1 Incident: the publish diff proposed a DROP

The first publish attempt after this order offered:

```sql
ALTER TABLE "chief_spend_cursor" DISABLE ROW LEVEL SECURITY;
DROP TABLE "chief_spend_cursor" CASCADE;
DROP INDEX "idx_llm_spend_ts";
```

**Not a bug in this repo.** There is no schema-diff tool here — no Drizzle, no
Prisma, no schema file, and `.replit` has no migration hook (its deployment is
`pnpm install`, `install:playwright`, `pnpm build`, `pnpm start`). The SQL comes
from Replit's own publish-time schema reconciliation.

**Root cause: dev was the stale side of the diff.** Verified read-only before
changing anything — `helium:5432/heliumdb` held `schema_migrations = {1}`, had
`llm_spend` and `idx_llm_spend_day`, and had neither `chief_spend_cursor` nor
`idx_llm_spend_ts`. Production had run migration 002 at boot. The diff took dev
as the reference, saw two objects in production dev had never heard of, and
proposed deleting them.

Dev was behind for a good reason: since L-3.4g the suite only runs against
throwaway clusters (`assertEphemeral`), so no gate run touches the real database.
That safety property has a cost — dev no longer drifts forward by accident, so it
must be moved forward deliberately.

**Why approving it would have been bad.** `schema_migrations` would still record
002 as applied while its table was gone, and `applyMigrations` skips what is
already recorded — so no later boot would recreate it. Spend reporting would have
failed against a missing table indefinitely. Same failure shape as the adopt-path
landmine in §5.1, arriving by a different road.

**Fixed** by adding `scripts/align-dev-db.mjs` and running it. Migrations and
nothing else — deliberately not `initDb()`, which also seeds the chief principal,
replays the rescue fixtures, GCs sessions and settles jobs left `running`; those
are boot concerns with no place in a schema alignment. It prints the backend as
`host:port/database` with no credentials, runs `assertNoDestructiveMigrations()`
before connecting, dry-runs by default, and applies inside the same transaction
production uses. Not in the gate, and it must never be — it is the one script
that intentionally touches a real database.

`heliumdb` went from `{1}` to `{1,2}`; both objects now exist there. Purely
additive, and the rescued chief job and its 20 leads were verified unchanged
afterwards. The diff should now propose nothing.
