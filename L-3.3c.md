# Order L-3.3c — Machine surface refuses a combination the app supports

Branch: `leadfinder-l33c-source-matrix`. Workspace: Leadfinder (Ad-Library-Finder).

## The defect, observed in production

The Chief's first commanded discovery, `source google_ads, target_type mobile, countries US, lead_count 20`, was refused by `POST /api/chief/jobs` with 400 and the message `source google_ads supports target_type cps only`. Michael states that Google Ads mobile discovery exists and works in the human UI. The machine surface added in L-3.3a is therefore refusing a combination the app itself supports, which means its source-to-target validation does not share a source of truth with the real job path.

## Scope

1. Find where the app's genuine source-to-target capability truth lives: what the human job-creation path accepts and what the runner actually dispatches per source. Report what you find and where L-3.3a's table came from, including whether it was inverted, stale, or invented.
2. Make the machine surface's validation read that same single source of truth. If no single shared representation exists yet, create one small one and point both paths at it; do not maintain two tables.
3. Correct any refusal messages so they state the real supported set for the named source.
4. Tests: the machine surface accepts exactly the source/target combinations the human path accepts, enumerated case by case from the shared truth, so the two can never disagree silently again; the original failing request from above now passes validation; at least one still-invalid combination still refuses with the corrected message; and one test proven able to fail by reintroducing the defect.
5. Report the full corrected matrix, every source with its supported target types, in chat and in the ledger entry. The Chief's console form is built from that matrix, so it must be exact.

## Out of scope

Everything else. No engine, queue, UI, email, auth, or contract-shape changes. The endpoint's paths, auth, ordering, and schemas stay byte-for-byte as documented in L-3.3a's ledger, except the corrected validation outcome and message.

## Ritual specifics

Blast radius first, in the ledger and chat. Gates: typecheck, tests, build. Audit rounds with the security framing confirming the shared truth cannot widen validation beyond the closed source and target vocabularies. Smoke in both modes on a separate port with the job runner disabled: baseline probes byte-identical, then the previously refused request accepted (job created, sits queued, never executed) and one invalid combination refused. Ledger entry. Merge to main and push when fully clean.

## Hard rules

Unchanged from L-3.3a: no destructive git, no force-push, no publishing, no secret changes, no schema changes, separate ports, never start a real scraping or verification run, never send or queue email, no external calls, halt after three failed attempts on one cause, ask rather than guess.
