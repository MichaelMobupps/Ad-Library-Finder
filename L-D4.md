# Diagnostic L-D4 — Commanded create answered 200 with no readable job id

Workspace: Leadfinder (Ad-Library-Finder). This is a diagnostic: read-only, no code changes, no fixes. Its output is a verdict; any fix becomes its own order.

## What happened in production

Today at roughly 15:20 UTC the Chief POSTed a commanded discovery to the live deployment: `source google_ads, target_type mobile, countries ["GB"], lead_count 20, external_id chief-discovery-2026-08-06-67e559ac90b5`. The Chief reports: the app answered 200, and no job id could be read from the response. The Chief therefore recorded "not commanded". Earlier today, before L-3.3c was merged, a deployment fired at 12:23 (71269e1) publishing the pre-L-3.3c tree; Michael has published at least once since. The C-3.3b client was smoke-tested against a mock built from L-3.3a's documented contract, never against the real create endpoint, because POSTing to live was forbidden. So the two leading hypotheses are: (A) the live deployment is not running current main; (B) the create endpoint's real response diverges from the contract documented in the L-3.3a ledger, and the mock inherited the documented version, hiding the divergence on both sides.

## Questions to answer, in order

1. **Did a job get created?** Read-only query against this app's database: any jobs row with `external_id` equal to `chief-discovery-2026-08-06-67e559ac90b5` (and, for completeness, `chief-discovery-2026-08-06-f670dfcc6f1f`, which should be absent since that request never left the Chief). If a GB row exists: its state, phase, owner, timestamps, and whether it is consuming budget right now. Also list all currently non-final jobs with their owners, so the known manual job is distinguished from any orphan.
2. **What does current main actually return on create?** Boot current main locally, separate port, job runner disabled. POST the exact production body with a throwaway external_id. Capture the exact status code, headers, and body byte-for-byte. Compare against the create response documented in the L-3.3a ledger section. State plainly: identical, or divergent, and where.
3. **What is the live deployment running?** Without creating any job on live: first prove from the code that a validation-refused POST is fully side-effect-free; then send to the live deployment one crafted create request that current main would refuse with a message that did not exist before L-3.3c (for example a body whose source/target pair passes the corrected matrix but fails a later validation step, chosen precisely from the code's validation order). The refusal text tells us which tree is live: the corrected vocabulary means post-L-3.3c, the old table's phrasing means the 12:23 tree, and a 200 with an HTML or non-JSON body means the request is not reaching the machine routes at all, which would point at the deployment serving something else entirely. Use the workspace `CHIEF_TOKEN` for auth without printing it. Read-only GETs to live status and to the GB job id from question 1, if one exists, are also permitted.
4. **Verdict.** One of: stale or broken deployment; contract-vs-implementation divergence on the create response; something else, named precisely. Plus: does an orphan GB job exist, and in what state. Plus: if the divergence hypothesis holds, quote the documented response schema next to the real one so the fix order can be written from this report alone.
