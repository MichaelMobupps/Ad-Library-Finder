# Order L-3.3a — Chief machine surface (status, commanded discovery jobs, results)

Branch: `leadfinder-l33a-chief-surface`. Workspace: Leadfinder (Ad-Library-Finder).

## Context, fixed, not to be re-litigated

- This is the app side of step 3.3, the discovery seam. The Chief will command this app to run a discovery job and will collect the results. The Chief-side client and console work is a separate order (C-3.3b) and is out of scope here.
- The pattern is already proven twice in this fleet. The Chief's inbound contract lives in its CONTRACT.md, and Prospector's status endpoint (order P-3.2a) established the app-side shape: identity comes from the token and never from the body; Bearer auth with case-sensitive scheme; constant-time compare via `crypto.timingSafeEqual` after a length check; 401 indistinguishable for missing, malformed, wrong or unset token; token trimmed on load with a warning; token never logged.
- The shared secret arrives as a new Replit secret named `CHIEF_TOKEN` on this app. Michael sets it after this order closes; its value will equal the Chief's `LEAD_FINDER_TOKEN`. Code must read it trimmed and treat unset as nothing-authenticates. Never print a secret value.
- Machine traffic goes app-to-app at the `.replit.app` addresses. The Chief will call `https://ad-library-finder.replit.app/leadfinder/...`, so every new endpoint must serve under `BASE_PATH` exactly as the existing `/api` routes do, and must not disturb the L2 legacy-redirect layer.
- Humans notice nothing. The cookie surface, OAuth, job UI, emails, and legacy links behave byte-for-byte as before.

## Scope

1. **Token loader.** Read `CHIEF_TOKEN` trimmed, warn at boot if the stored value carried surrounding whitespace, count it as loaded only if it can actually authenticate. Constant-time comparison. The token opens only the `/api/chief/*` paths below; it must not open any cookie-authenticated path, and a cookie session must not open any `/api/chief/*` path. Both directions get tests.
2. **`GET /api/chief/status`**, matching Prospector's contract exactly: 200 with `Cache-Control: no-store` and `{app: "leadfinder", ok: true, accepting_jobs, active_jobs, spend_today_usd, server_time}`; 401 indistinguishable; 503 on a failed read, never a fabricated value. `accepting_jobs` answers whether a new job would be accepted right now under this app's own queueing rules; `active_jobs` counts running jobs; `spend_today_usd` is `0` and truthfully so, because this app has no paid vendors, with a source comment saying exactly that.
3. **A system principal for commanded jobs.** Chief-created jobs are owned by a non-human principal, not by any Google account. They send no email on completion or failure. Decide and report whether they appear anywhere in the human UI; invisible is acceptable, but if visible they must be clearly labeled as the Chief's. A human's own jobs are entirely unaffected.
4. **`POST /api/chief/jobs`** creates a discovery job. Closed body, refused on any unknown field: `source` (one of `google_ads`, `meta`, `affplus`, `appgoblin`), `target_type` (`mobile` or `cps`), `countries` (non-empty array of supported country codes, refused if any code is unsupported), `lead_count` (20, 50 or 100 only; unlimited does not exist for commanded jobs), `external_id` (required string, the idempotency key, length-capped and refused over-length rather than truncated, stored byte for byte). Re-sending the same `external_id` returns the existing job rather than creating a second one, mirroring the Chief's own idempotency rule. `Content-Type: application/json` required; malformed JSON and oversize bodies rejected before auth; 401 precedes 404, all mirroring the Chief's contract ordering. Success returns the job id and initial state. The job enters this app's normal queue and runs with this app's normal engine; nothing about how discovery works changes.
5. **`GET /api/chief/jobs/:id`** returns the job's state using this repo's real state vocabulary (report it), progress as the human UI sees it (current step, leads so far), and timestamps. **`GET /api/chief/jobs/:id/leads?offset=&limit=`** returns completed results as JSON with stable ordering, `limit` defaulting to 50 and capped at 100, each page well under the Chief's 64 KB response ceiling. The lead object shape is derived from what this app actually stores; report it in full. Both endpoints answer 404 for any job the chief principal does not own, so human jobs are invisible to the token, with a test proving it.
6. **Tests**, following this repo's existing conventions: auth in both directions from item 1; the status contract; every validation refusal in item 4; idempotent create; pagination bounds and ordering; human-job invisibility; a commanded job creating no email work; and at least one test proven able to fail by reintroducing its defect. Test boots must not start the job runner, so created jobs sit queued and are never executed during tests or smoke.
7. **Report**, in chat and in the ledger entry, the complete contract as built: every path in both modes, auth rule, status codes and their ordering, full request and response schemas including the lead object and the state vocabulary, one real captured exchange per endpoint with the token redacted. C-3.3b will be written from that report alone.
